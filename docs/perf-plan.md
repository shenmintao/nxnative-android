## 2. 已知事实（不要重新调查）

历史数据原出自 `docs/PORT_STATUS.md`，已按阶段 4 原样迁移至 `docs/perf-log.md` 的“历史”一节。

**设备与系统**
- 设备是 TB323FU（SM8850P / Adreno 840，Android 16）。游戏运行时屏幕为 120 Hz，帧间隔都是 8.33 ms 的整数倍；平均 57 fps 实际是 16.7 ms 和 25 ms 两种间隔交替。
- 游戏在前台时，CPU 频率上限是 1,996,800 / 2,438,400 kHz。硬件最高是 3,628,800 / 4,608,000，游戏退出后恢复到 3,513,600 / 4,512,000。游戏分类、Game Mode 的性能模式、关闭 ADPF 都不改变这个上限。
- GPU 频率稳定在约 826 MHz，最高频率节点没有读取权限。
- 帧率对 CPU 频率敏感：有一次去掉游戏分类，大核平均频率从 2.29 降到 1.70 GHz，帧率从 57.3 掉到 50.2。

**已有性能数据**
- 原生 1080p（私有包，`DM_RENDER_SCALE=1.2`）：固定视角 57.1–57.7 fps，移动 58.2–59.7 fps。固定视角下每帧的串行链约 17.4 ms：录制翻译 8.3 ms + 游戏自身 2.1 ms + 等 GPU 6.8 ms + 其他 0.2 ms。
- 游戏的底座动态分辨率：10-29 用旧代码实测时落在 1280×720。在当时的代码下，720p、899p、1080p 的帧率都约 54 fps，说明当时瓶颈在 CPU；之后 CPU 部分已经缩短。**目标配置还没有用当前的私有包测过**，这正是阶段 1 要回答的问题。
- 管线编译卡顿：冷缓存时 60 秒内驱动编译 26 次，共 374 ms，单次最长 60 ms；用 1,063 个记录过的 key 预热后，降到 10 次、80 ms。正式版不带预热 key，全新安装时缓存是冷的。
- `DM_FPS_HOLD` 默认是 on，帧迟到时会把帧率降到 30 档。10-29 实测：on 是 31.4 fps，off 是 53.9 fps。

**APK 与源码**
- 正式版：`ROOM\ZeldaBreathOfTheWild.apk`，sha256 前缀 41a37988，就是平板上现在装的版本（30 fps、掌机模式）。它的可调试版是 `<OPT>\buffer-abi-debug.apk`（5a0ac3d0），由同一份正式源码构建。
- 平板上保存的应用设置里 `docked=0`，它会覆盖 `env.txt` 里的 `DM_OPMODE`（`front_android.c`）。切底座时，设置文件也要一起改。
- 代码备份分支：`backup/codex-goal-2026-11-01`（e1c806ce）。

**私有性能栈**（只存在于私有源码，正式源码里没有）
- 源码在 `<OPT>\retire-worker-source\`。和正式源码比较时忽略行尾 CR，差异如下：
  - `gfx_vk_core.c` 约 240 行，`gfx_vk_exec.c` 约 135 行，`gfx_vk_tex.c` 75 行，`gfx_vk.h` 23 行，`gfx_vk_present.c` 7 行；
  - 新增 `gfx_vk_encode.c`（789 行）；
  - 另有 `hle_nvn.c`、`sync_trace.h`，以及 `loader.c` 里把缩放上限放宽到 1.25 的改动。
- APK：`<OPT>\retire-worker-1080-debug.apk`（e091ee86）。
- 基准测试用的开关（出自 `<OPT>\leafbuf-bench-l0-20261101-083220\env.json`）：
  - `DM_VK_ENCODE_THREAD=1`、`DM_VK_TAIL_DRAWS=256`、`DM_PIN_REPLAY=prime`
  - `DM_VK_GUEST_NOTIFY=1`、`DM_VK_DEFER_PARTS=1`、`DM_VK_CMP_CONSTANT=1`、`DM_VK_DESCRIPTOR_BUFFER=1`
  - `DM_FPS_HOLD=off`、`DM_OPMODE=1`、`DM_FPS_TARGET=60`、`DM_RENDER_SCALE=1.2`
- 已证实有效：
  - 编码线程 + 尾批 256 + 绑定大核：+3.9%；
  - GPU 完成后提前通知游戏（guest-notify）：+3.4%；
  - descriptor buffer：+1.05%；
  - 管线预热：减少卡顿。
  - `DM_VK_DEFER_PARTS` 减少了等待次数，但 fps 收益在噪声内。
  - `DM_VK_CMP_CONSTANT` 是比较采样器（NEVER/ALWAYS）的兼容路径，用来避开不受支持的浮点深度拷贝，没有证明有性能收益。
- 已证伪，不要重试：
  - 独立回收线程、CRC 管线 key、descriptor 字节编码线程、免计数 NVN 入口、buffer 查询绕过大栈；
  - pending-write 扫描截断、buffer cells、把同步 CB 生命周期放到 worker 上、前缀提交（−8.9%）；
  - ADPF 余量和图形管线 hint、`DM_NVN_ASYNC`、所有帧线程都绑大核（−13%）；
  - 更小的首批、uniform 拷贝线程、present 快照、独占锁重试暂停；
  - 只读深度的 store 优化、合并屏障、用 SPIRV-Tools 优化着色器、Turnip 驱动。

## 4. 测量规范
- 帧时间只用 SurfaceFlinger 的实际呈现时间，预热 60 s 之后才开始计。
- 每次运行记录这些指标：
  - 平均 fps、超过 17.5 ms 的间隔占比、P99、最大值、超过 50 ms 和超过 100 ms 的次数；
  - 内部主 pass 尺寸、每帧绘制数、运行时管线编译次数；
  - CPU 上限、测试前后的温控等级、音频回调是否正常。
- 噪声：同一配置两次运行之间约有 ±0.5 fps 的差异。比较改动时按 OFF/ON/ON/OFF 测；提升 ≥ 1 fps，并且两个 ON 都高于两个 OFF，才算有效。
- 冷却：每轮之间熄屏至少 90 s。开始前 CPU 或 GPU 温控等级 ≥ 2 时先等待，最多 5 分钟，并在结果里注明。只记录，不调查原因。
- 一组测试结束后，再恢复正式版、原始设置和主存档并熄屏；同一组的各轮之间不用重装。
