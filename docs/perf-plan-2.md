## 2. 线索（来自计划 1，不要重新测）

- **计算管线不在预编译列表里。** PPE1 只记录图形管线：`gfx_vk_exec.c` 里 `vkCreateComputePipelines` 那条路径不调用 `pipe_record`。F 组第一轮移动测试中，一次 126 ms 的计算管线创建造成了一个超过 100 ms 的长帧。
- **固定视角的长帧不是管线编译造成的。** F 组固定视角窗口里运行时管线创建为 0，长帧仍有 14–24 次。
- **长帧没有规律。** 间隔从 0.1 s 到 25 s 不等，经常两三个扎堆。
- **性能栈可能贡献了一部分长帧。** 42 ms 以上的帧：B（原代码，HOLD off）每 2 分钟 11–15 次，F（带性能栈）41–52 次。但 B 的帧本来就慢，在这个阈值上不完全可比，需要归因确认。
- **F 组测的是"新装后首次启动"。** 每轮都新建空的 DM_ROOT，驱动管线缓存（`vk_pipeline_cache.bin`）是空的，1,199 个 key 要在 3 个低优先级线程上从头编译，测量窗口内可能还在编译。正常使用时，驱动缓存会存进 DM_ROOT，第二次启动起就是缓存命中。本计划的验收要模拟正常使用（见阶段 0 第 3 步）；首次启动单独记录。
- **可复用的工具**：
  - 私有线里的 `<OPT>\retire-worker-source\nxnative\dm\android\sync_trace.h`：ATrace 作用域，只在 `DM_TRACE_SYNC=1` 时生效。
  - 分析脚本 `<OPT>\analyze_fence_chain.py`、`analyze_serial_frame_chain.py`、`analyze_serial_frame_states.py`、`analyze_scheduling_profile.py`、`analyze_work_profile_scopes.py`。
  - 样例数据 `<OPT>\fence-profile-system-c1-e1-d1-s1-trace-bench-20261031-190809\`。
  - 当前分支已有 `DM_VK_PIPELINE_TIMES=1`，会记录运行时的管线创建。

### 阶段 2：修复（必做 1 项，另外最多 3 项）
- **2a（必做）计算管线预编译**：把计算管线也写进预编译列表，启动时预编译。可以新增记录类型，也可以扩展 PPE1 格式；旧文件要么能读，要么被安全忽略。验收：暖启动的移动路线 120 s 内，运行时计算管线创建为 0 次。
- **2b 按归因修复**：对选出的每个类别写清原因、改法、预计减少多少迟到帧，再按 OFF/ON/ON/OFF 验证。参考方向：
  - 后台预编译抢核：只影响首次启动，可以减少线程数或绑到小核；
  - 资源首次创建或上传：复用或提前创建；
  - 编码线程排空：做组件对照（见下一条）；
  - 游戏自身工作：主机侧通常改不了，如实报告。
- **性能栈组件对照**：只在"编码线程排空"或"调度"类显著时做，最多 2 个组件。只改环境变量（`DM_VK_DEFER_PARTS`、`DM_VK_GUEST_NOTIFY`、`DM_VK_TAIL_DRAWS`、`DM_PIN_REPLAY`），按 OFF/ON/ON/OFF 测迟到帧占比。
- **保留标准**：迟到帧占比相对降低 20% 以上（例如 3.5% 降到 2.8% 以下），或 > 50 ms 次数降低 30% 以上，同时平均 fps 下降不超过 0.3。达不到就放弃。
- **噪声**：同一配置两次运行之间，迟到帧占比约差 ±0.3 个百分点；> 50 ms 次数波动很大（14–35），所以判断以迟到帧占比为主。

   要求单元测试全过，Vulkan 验证层 0 错误。
2. 构建 debug 和 release 版。用 `--warm-start` 跑验收表：固定 ×2、移动 ×2、30 分钟浸泡；首次启动移动 ×1 只记录；release 做冒烟测试。

## 7. 阶段 1 续："未知"已查明（2026-11-02 补充，停止条件解除）

**发现**：对 `runs/20261101-235117-P2-trace-warm-fixed-retry` 的 trace 和 `attribution-warm-fixed/` 做离线分析，不需要重测。
- 提交线程（tid 364）睡眠等待期间，另一个游戏线程（tid 343）在运行：在 157 个"未知"迟到帧里，有 156 个是 343 的运行时间占了这段睡眠的一半以上；合起来算，343 运行覆盖了 364 睡眠时间的 91%。
- 22 个 > 50 ms 的间隔：343 在帧窗口内运行中位 49.8 ms，最长 110 ms。其中 16 个，364 在 343 停止运行后 200 µs 内被唤醒（中位 47 µs），说明是 343 做完后把工作交给 364。
- 25–50 ms 的"未知"迟到帧：343 运行中位 24.5 ms。准时帧里 343 运行中位 7.8 ms，364 很少等它。
- 这些突增期间，343 跑在 cpu0–5（上限 2.0 GHz 的集群），平均频率只有 1.58 GHz（> 50 ms 的帧）/ 1.76 GHz（25–50 ms 的帧）；364 则绑在大核 cpu6–7 上。
- 343 也是执行 `NVN explicit wait` 和 `guest wait` 的线程，很可能是游戏的主循环线程。

**结论**："未知"实际是"另一个游戏线程的 CPU 工作突增"。原归因脚本只统计提交线程上的游戏 CPU，所以把它记成了未知。录制翻译（12.9%）和等 GPU（16.9%）都低于 20% 门槛，不再优化这两条路径。

## 8. 热点已定位：并行任务分发锁的争用（2026-11-02 补充；做完 7.3 的调度实验后再执行）

**分析**（离线完成，用的是 `runs/20261102-092414-P2-cpu-warm-fixed/cpu.data` 的全进程采样，加上 `patched_v1114112/main.patched.bin` 的反汇编）：
- `main+0xef62dc` 是游戏并行任务（parallel-for）的"领一段工作"函数。`[x21+0x1c]` 上有一把自旋锁，保护"下一个索引"（`+0x94`）和"总数"（`+0x90`）；线程领到一段后逐项执行（`0xef6450` 处的虚函数调用）。
- 这个函数里有一个空转轮询：标志 `[x21+0x98]` 置位、而 next == 0 时，非 0 号线程领不到工作，就"加锁 → 检查 → 解锁 → 回到 `0xef6354` 再加锁"（回边是 `0xef63e8` 的 `cbz w14`），在锁上反复抢。
- 慢帧线程（这轮是 tid 3619，对应 trace 里的 343）有 41% 的周期花在这个函数的加锁循环里，临界区里一个样本都没有。热点指令：
  - `0xef637c`（stxr 失败后重试）14.3%
  - `0xef6368`（ldaxr）13.4%
  - `0xef6378`（stxr）6.6%
  - `0xef6370`（clrex）3.8%

  也就是说，它看到锁空了，但 store-exclusive 一再失败。
- 两个工作线程（3873/3874，对应 trace 里的 369/370）各有 47–48% 的周期在这个函数里：约 30% 在加锁，10–11% 在临界区，约 3% 在解锁，约 2.5% 走"没领到工作、再来一次"的回边。
- 结论：这是 LL/SC 自旋锁在争用下的饥饿。两个工作线程空转轮询，一直占着锁所在的缓存行，慢帧线程长时间抢不到锁，正好对应 25–110 ms 的慢帧。原因不是计算量大。

**实验**（计入阶段 2 的修复名额；每项按 OFF/ON/ON/OFF 测迟到帧占比和 > 50 ms 次数；保留标准不变）：
- **8a 让空转轮询退避（优先）**：在 `0xef63e8` 的"没领到工作"回边上加 spin gate，每次空转都让出 CPU（`sched_yield`，或睡几微秒），不要像现有 gate 那样先空转 2 ms。
  - 先写成只针对 BotW 1.9.0 main（build ID `cd57b23f…`）的补丁来验证。
  - 有效的话，再推广成重写器的通用规则：一个轮询循环里，除了一对加锁/解锁和写常量状态，没有别的副作用，才允许加 gate。
- **8b LL/SC 改为 LSE 原子指令（第二优先）**：本机所有核都支持 LSE。把六条指令的加锁循环 `ldaxr/cbz/clrex/b/stxr/cbnz` 原地改成 `mov w14,wzr; casa w14,w10,[x9]; cbnz w14,<回到外层读>`。
  - 长度不变，寄存器和标志的语义一致（退出时 w14 = 0）。
  - 先只改这个函数里的两处来验证；推广到其他地方之前，要确认没有分支跳进这六条指令的中间。
- 两项分开测，不叠加。8a 达到保留标准，就只保留 8a。

### 8a 更新（2026-11-02）：直接移植上游 nxnative 现成的规则
- 上游 nxnative 在 2026-10-28 的提交 `2c31212` 已经修好了同一个问题。`dm/games/01007EF00011E000/README.md` 的 CPU 一节（"Resolved: CPU hitches"）记录了一样的现象和分析：主线程几乎抢不到锁，30–210 ms 的 CPU 卡顿每 1–10 秒出现一次。
- 上游的修法：在重写器的 spin wait 规则里加入"加锁轮询"这种情况（`patch_nso.py` 的 `spin_lock`、`spin_store`），让这个轮询的回边经过现有的 spin gate，工作线程每轮之间就会把锁让出一会儿。
- 上游在 Mac（M2 Max，佐拉领地）上的效果：站着不动时，超过 30 ms 的 CPU 帧从每 30 s 2.8–6.3 次降到 0 次；转视角时从 6.3–13.3 次降到 0 次；帧工作量的 p99 从 20–21 ms 降到 8.3 ms。
- 我们的子树和 nx2android 上游都还没有这条规则（`grep 'def spin_lock'` 都是 0）。我们 `main` 的 spin gate 是 308 个，只覆盖了 `0xef635c` 和 `0xef63f0` 的纯读外层循环。
- 做法：
  - 只移植 `patch_nso.py` "Spin waits" 一节里的相关改动：上游这一节比我们多 106 行、少 13 行，主要是 `spin_lock`、`spin_store`、`SPIN_STORES` 和对 region 搜索的修改。并行化扫描（`find_spin_regions` / `spin_heads_with_region`，来自 `0b3fa7e`）可以不带。
  - 重新生成 BotW 的重写模块。预期 `main` 的 spin wait 从 308 个变成 310 个，新增的两个是 `0xef62dc` 里的任务队列轮询和 `0xf82230` 的状态设置循环。
  - 把新模块推到平板上。
- 测试：旧模块和新模块按 OFF/ON/ON/OFF 对照，看迟到帧占比和 > 50 ms 的次数。达到保留标准，就不再做 8b。
